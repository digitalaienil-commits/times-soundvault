# Authentication

## Runtime

Times SoundVault uses Better Auth 1.6.29 with PostgreSQL 17. Better Auth owns
user, account and database-session lifecycle. Local email/password is enabled
only outside production; production uses exactly one configured corporate
provider (`google` or `microsoft`). There is no public registration route.

`src/lib/auth/auth-factory.ts` is the single configuration factory used by the
application and operational scripts. Security-relevant choices include:

- database-backed sessions with no cookie cache;
- encrypted OAuth tokens and database-backed OAuth state;
- disabled account linking and implicit email linking;
- database rate limiting, with stricter sign-in rules;
- exact trusted origins and secure cookies on HTTPS;
- server-owned role input;
- active team-access validation when creating and reading sessions.

## First sign-in

1. Admin or bootstrap creates a pending assignment for an exact normalized
   email.
2. The configured provider authenticates the identity.
3. Before user creation, SoundVault verifies that a pending assignment exists
   and supplies its one role server-side.
4. The committed Better Auth user/provider account is bound to that assignment
   in a transaction.
5. The session is created only after active access is confirmed.

Wrong emails, suspended records, reused assignments and unsupported providers
fail closed. Activation retries for the same verified identity are idempotent.

## Session policy

Session lifetime, refresh age and freshness live in
`src/lib/auth/constants.ts`. Role changes and suspension delete every database
session for the target user. Every protected request also checks the current
assignment, so navigation visibility or a stale cookie never grants access.

## Migrations

```bash
pnpm auth:generate
pnpm auth:migrate
```

`0000-better-auth.sql` is generated by the pinned Better Auth CLI.
`0001-team-access.sql` is the reviewed application migration and is tracked in
`auth.soundvault_migration`. CI applies both from an empty database.
